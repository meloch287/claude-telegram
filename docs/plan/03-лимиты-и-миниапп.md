# Лимиты подписки и мини-апп

## Главное ограничение, которое определяет весь дизайн

**У SDK нет метода «покажи остаток лимита».** Данные приходят событием в потоке
сообщений сессии:

```ts
type SDKRateLimitEvent = {
  type: 'rate_limit_event';
  rate_limit_info: SDKRateLimitInfo;
  session_id: string;
  uuid: UUID;
};

type SDKRateLimitInfo = {
  status: 'allowed' | 'allowed_warning' | 'rejected';
  resetsAt?: number;
  rateLimitType?: 'five_hour' | 'seven_day' | 'seven_day_opus'
                | 'seven_day_sonnet' | 'seven_day_overage_included' | 'overage';
  utilization?: number;
  overageStatus?: 'allowed' | 'allowed_warning' | 'rejected';
  overageResetsAt?: number;
  overageDisabledReason?: …;
};
```

В типах прямо написано: «Rate limit information for **claude.ai subscription**
users». То есть событие рассчитано ровно на наш случай.

### Что из этого следует

1. Мини-апп показывает **последнее известное** состояние, а не текущее. Рядом
   обязательна отметка «данные на такое-то время» — иначе это враньё.
2. Пока пользователь не отправил ни одной задачи, лимитов не видно вообще.
   Показываем честное «данных пока нет, напиши агенту что-нибудь».
3. Событие приходит не на каждый ответ. Значит хранить надо не «текущее
   значение», а историю с отметками времени.

## Что показываем

### Пятичасовое окно

`rateLimitType: 'five_hour'` → `utilization` и `resetsAt`. Отсюда:

- полоса «выбрано N%»
- «обнулится через 2 ч 14 мин»

### Недельное окно

`seven_day`, плюс отдельные `seven_day_opus` и `seven_day_sonnet` — у Opus и
Sonnet лимиты считаются раздельно. Значит в интерфейсе это **три разные полосы**,
а не одна: свалить их в кучу — потерять смысл.

### Перерасход

`overageStatus` и `overageResetsAt` — состояние доплаты сверх лимита.
Показываем, только если `overageStatus` вообще пришёл: у большинства подписок
его не будет, и пустой блок только запутает.

### Коты

Уровень кота считается по **суммарным токенам за всё время** — это уже работает
и от лимитов не зависит. Лимиты и коты живут рядом, но не связаны: лимит
обнуляется каждые пять часов, кот не должен от этого мельчать.

## Хранение

Новая таблица:

```sql
CREATE TABLE rate_limits (
  user_id     INTEGER NOT NULL,
  limit_type  TEXT    NOT NULL,   -- five_hour, seven_day, seven_day_opus, …
  status      TEXT    NOT NULL,
  utilization REAL,
  resets_at   INTEGER,
  seen_at     INTEGER NOT NULL,
  PRIMARY KEY (user_id, limit_type)
);
```

Одна строка на тип лимита, перезаписывается по мере поступления событий.
`seen_at` — чтобы показать возраст данных.

## Где ловим

В `Conversation.#handle()` добавляется ветка на `message.type === 'rate_limit_event'`.
Оттуда — колбэк `onRateLimit`, дальше в базу, как уже сделано для расхода токенов.

Отдельно: при `status === 'rejected'` или `'allowed_warning'` бот сообщает об этом
в чат сразу, не дожидаясь, пока пользователь откроет мини-апп. Упереться в лимит
посреди работы и не понять почему — худшее, что может случиться.

## Экран мини-аппа

```
Мой Claude-кот
план: подписка · данные на 14:32

[кот]  Кот-рефакторщик, уровень 4 из 10

Пятичасовое окно      ▓▓▓▓▓░░░░░  47%   обнулится через 2 ч 14 мин
Неделя, Opus          ▓▓▓░░░░░░░  31%   обнулится в четверг
Неделя, Sonnet        ▓▓░░░░░░░░  18%   обнулится в четверг

Всего за всё время: 420 000 токенов · $12.48
До «Кот-дебагера»: 330 000 токенов
[галерея котов]
[достижения]
```

Требования к доступности те же, что уже выполняются: полосы объявляются фразой
целиком через `aria-valuetext`, статус передаётся словом, а не только цветом,
контраст не ниже 4.5:1 в обеих темах.

## Откуда берётся замер, когда процента нет

Процент подписки этим токеном недоступен: событие \`rate_limit_event\` его не
несёт, а метод плана отвечает \`rate_limits_available: false\` и
\`subscription_type: null\` — у токена от \`claude setup-token\` нет области
профиля. Проверено обоими способами, плюс командой \`/usage\` внутри сессии:
она отдаёт только расход сессии.

Вместо процента шкалы показывают свой замер по транскриптам Claude Code
(\`src/subscription-usage.ts\`). Почему не по своей таблице расхода: она знает
только то, что прошло через бота, и считает лишь input и output. Подписка
тратится на всё, что запускает Claude Code в контейнере, включая субагентов,
и в счёт идёт ещё и кэш. Разница огромна: за пять часов вышло 147 млн токенов
с кэшем против 388 тысяч без него.

Экономия на чтении: сперва отбрасываются файлы, не менявшиеся с начала окна —
внутри окна записей в них быть не может. За пять часов остаются единицы файлов,
подсчёт занимает десятки миллисекунд, ответ кэшируется на минуту.

Чего замер не знает: работы с других машин. Claude Code в терминале на ноутбуке
тратит ту же подписку, но его транскрипты лежат там, а не на сервере.

## Открытые вопросы

- Приходит ли `rate_limit_event` при работе по API-ключу, или только по подписке?
  Судя по комментарию в типах — только по подписке. **Не проверено.**
- Как часто приходит событие: на каждый ответ или при изменении? **Не проверено.**
  От этого зависит, насколько свежими будут данные.
- ~~Есть ли у Claude Code команда `/usage`, которую можно дёрнуть принудительно?~~
  **Да, и это оказалось главным.** У `Query` есть метод
  `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET()`: он отдаёт
  структуру за `/usage` — стоимость сессии и сразу все окна лимитов
  (`five_hour`, `seven_day`, по моделям) с процентом и временем сброса.
  Событие `rate_limit_event`, на которое бот полагался, приносит по одному
  окну и часто без процента — отсюда и пустая статистика. Теперь окна
  забираются методом после каждой задачи, не чаще раза в минуту, и
  принудительно по `/status`. Событие оставлено: только оно приносит статус
  (предупреждение, отказ), которого в методе нет.
