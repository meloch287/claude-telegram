# Архитектура

## Из чего состоит

```
Telegram ──► бот (grammy, long polling)
                │
                ├─► Conversation ──► Claude Agent SDK ──► бинарь claude ──► api.anthropic.com
                │                         (подпроцесс)                        (может через прокси)
                │
                ├─► SQLite: пользователи, чаты, расход, лимиты, достижения
                │
                └─► HTTP-сервер мини-аппа ──► Caddy/nginx ──► HTTPS-домен
```

Всё в одном процессе Node внутри одного контейнера. Разносить нечего: нагрузка —
один человек, а связность между частями высокая (мини-апп читает ту же базу, что
пишет бот).

## Почему вход по подписке

`claude setup-token` выдаёт долгоживущий токен и прямо говорит: «requires Claude
subscription». Токен уходит подпроцессу агента переменной `CLAUDE_CODE_OAUTH_TOKEN`.
Что это поддерживаемый путь, видно по типам SDK: `ApiKeySource` включает
значение `'oauth'`, а событие `SDKRateLimitEvent` описано как «rate limit
information for claude.ai subscription users» — то есть SDK рассчитывает на
пользователей подписки.

Запрет в документации SDK звучит так: третьим лицам нельзя *предлагать вход через
claude.ai пользователям своего продукта*. Здесь этого нет: сервис не выдаёт чужим
людям доступ к чьей-то подписке, он передаёт дальше токен своего же владельца.
Отсюда важное следствие для дизайна: **сервис однопользовательский по смыслу**.
Белый список `ALLOWED_USER_IDS` — не украшение, а часть этого рассуждения.

### Грабля, на которую уже наступили

`env` в опциях SDK **заменяет** окружение подпроцесса целиком, а не дополняет.
Поэтому `process.env` расстилается руками — иначе у подпроцесса не будет даже
`PATH`.

И более коварное: неиспользуемый способ входа нужно **удалить**, а не просто не
задать. Унаследованный `ANTHROPIC_API_KEY` рядом с токеном подписки молча
победит, и работа пойдёт по деньгам вместо лимитов. Это в `buildEnv()`.

## Почему одна живая сессия на чат

`query()` со streaming input держится, пока не закрыта очередь сообщений. Пока
она жива, доступны `interrupt()`, смена режима разрешений и модели на лету.
Альтернатива — новый `query()` на каждое сообщение с `resume` — всё это теряет и
платит за прогрев на каждой реплике.

Расплата: процесс упал — сессия оборвалась. Лечится тем, что `session_id`
сохраняется в базу и при следующем сообщении сессия поднимается через `resume`.

## Учёт расхода

`total_cost_usd` и `modelUsage` в streaming-сессии **накопительные**: каждый
`result` несёт итог с начала сессии, а не за ход. Суммирование по всем `result`
завысило бы расход в разы. Поэтому `Conversation` хранит прошлый итог и пишет в
статистику разницу.

Считать надо по `modelUsage`, а не по `usage`: второй покрывает только главный
цикл и занижает расход на задачах с субагентами.

## Разрешения

Мост `canUseTool` → карточка с кнопками. Колбэк можно держать открытым сколько
угодно — документация это разрешает явно.

Чего делать нельзя: возвращать `null`. Это fail-closed — вызов инструмента
блокируется навсегда, без ошибки и без таймаута. Поэтому у каждого запроса есть
таймаут, обработчик `abort` и аварийный отказ, если карточку не удалось
отправить.

## Открытые вопросы

- Нужно ли несколько одновременных проектов в одном чате, или хватает
  переключения `/project`? Пока хватает.
- Стоит ли выносить мини-апп в отдельный процесс, если появится второй
  пользователь? Пока нет второго пользователя — вопрос теоретический.
